# State protocol

`state.json` schema_version is 2. Only the supervisor writes it. The schema and pure transitions are defined by `internal/state/workflow.go` and `internal/workflow`; `factory workflow next <snapshot> <event>` prints a proposal without side effects. A malformed or unsupported snapshot blocks recovery.

`pipeline_stages` is the exact resolved selection; `needs_design` is true exactly when it includes design. Persist app-supplied effective agents without resolving them again.

Preserve id, incarnation, holder_generation, repo, worktree, branch, start_commit, authorized, agents and supervisor. Revision increases once per new processed event. Workflow holds runs, active_run, pending effect, nested return_to, gate and suspended correction. Each run records stage, role, round, loop, heads, paths and outcome. Local stage receipts cache transport state, never choose the next stage.

Stack entries are ordered bottom to top: branch, parent, head, base and title. PR entries additionally record number, URL and observed head/base SHA. Findings have stable IDs, owning stage/layer, severity, disposition and evidence. Recipe stores commands, working directories, sources and source digest. Verification binds to that digest and ordered head/base tuples. Confirmation records the handoff item, exact heads, receipt and time.

Events require id, kind, revision, incarnation, holder_generation and real UTC at. Kinds: start, checkpoint, commands, discovery, comments_preference, effect_received, result, approval, changes, answers, design_return, design_comments, cap, retry, observe, comments_start, comments_stop, lost_run, handoff and continue. Developer events additionally carry item_id, artifact_revision, actual answer and receipt or conversation reference. Cap increments must be positive, and so must a retry's increment once stage_retries is spent. A handoff `continue`, and an `answers` event with `new_request: true` after implementation has started, start a new request: `loops.request` goes up by one, review_fix, qa_fix and ci_fix count from zero under the same limits, and a `request` history row records the previous request's usage and the receipt. The engine refuses `new_request` on any other event. After implementation has started, a commands event that changes the digest is refused while a run is active or a developer item other than the handoff offer, the commands question, an implementation failure or question, or the last run's failure that it settles is open; a retry or answer of that implementation item then runs on the new recipe. A commands event may carry `detail`, the body of the commands item it opens. When the last run of implement, review, qa or pr failed and its failure item is open, a resolved recipe with a changed digest resolves that item and re-runs the work without a developer receipt, from implementation (or pr once PRs exist) when the new recipe invalidated the stage's evidence, and an unresolved recipe replaces the failure with the commands item whose resolution does the same. Each settled failure adds one to `loops.used.rediscovery`, capped by stage_retries. Once it reaches the cap, a changed recipe under the failure is still accepted but re-runs nothing; the failure stays open for a developer `retry`, which re-runs from implementation (or pr once PRs exist) when the new recipe invalidated the failed stage's evidence, and otherwise re-runs that stage. A positive retry `increment` always raises stage_retries. A discovery event carries `note: {event, detail}` with event `discovery started`, `discovery started again`, `test noted` or `commands recorded`, and only adds that activity row. An observe event must carry the stack and, once PRs exist, every published PR whose branch is still in that stack; the PR of a removed layer may drop. Agent results cannot grant approval, accept a risk or confirm done. A comments_preference event recorded from the launch line's `--comments on|off` carries answer `on` or `off` and receipt `launch`; it sets `comments_asked`, so the analyst never asks again. After that, `comments_start` (answer and receipt required) turns watching on and clears a recorded stop, and is refused once the factory is done; at an open handoff with no run it withdraws the offer and dispatches pr, and the pr run that was active when comments were turned on, if its only missing readiness is comment handling, dispatches pr once more instead of being rejected; any later pr result with comments unhandled is rejected as before. `comments_stop` turns it off.

Stage results use schema_version 2, run_id, input_heads, output_heads, status, findings, evidence and outputs. Status is done, blocked or failed. `data.failure` names why a run failed; in implement, review, qa and pr a `failed` or questionless `blocked` result re-dispatches the stage while the run's retries are below stage_retries, with an `auto retry` history row, unless it is `setup`, `stack_start`, `stack_health`, `recipe_missing`, `seed`, `sign_in`, `interactive_challenge` or `uncertain_outcome`, which open the failure item at once. The engine fixes only shape slips that lose nothing: a string in `evidence.checks` becomes an `evidence.notes` entry `check: <text>`, and commit SHAs in `input_heads`, `output_heads` or `evidence.heads` become `[]` with a note, only while the factory has no stack and each SHA is the start commit. Everything else is rejected with its exact reason. A clean review/QA uses pass evidence tied to its input heads. Engineer and CI check evidence includes every command, directory, head, exit_status and log path. The supervisor independently checks the output heads and evidence before the result event.

The commit script accepts state path, proposal path and current supervisor session identity. Its OS-released lock prevents concurrent stale writes. It preserves unowned metadata and atomically replaces the file. Duplicate event delivery is a no-op. Never edit state to bypass a rejected proposal.

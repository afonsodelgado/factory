# Developer answers

Persist attention before asking. Each item has a unique id, kind, stage, artifact revision, created_at and unresolved resolved_at. Gates and caps remain visible across backward loops. New design revisions get new item IDs. Cap items contain loop, limit_key, used, allowed and open findings.

Recognize `<item id> answers:`, `changes:`, `reply:`, `continue:`, `done:` and `handled:` messages. Preserve the exact developer text and node operation receipt, or a direct-conversation reference. Receipt delivery is not committed approval. `handled` is never proof that a cap, finding, check or handoff is satisfied. A `design_return` item opens only in a pipeline with a design stage; without one, the plan's design findings are listed on the plan gate, and approving the plan records them as accepted risks. A `design_return` answer is free text: revising the design returns the listed findings to design (`approved: true`), keeping the plan records them as accepted risks. Older answers say accept and decline for the same choices. A `commands` answer gives missing commands or says what the developer set up on this node: save typed commands with `factory workflow record --yours`, run discovery again for what is still blank, then commit the re-resolved recipe through a `commands` event.

Run `factory attention resolve` to validate an item; it changes nothing. Convert the actual answer to a typed workflow event, run the pure rules, then commit the proposal before acting. Do not apply an unvalidated printed edit as a substitute for the workflow transition. Match item identity and artifact revision; stale answers are rejected.

Under FACTORY=1 ask in plain text after persistence. Number questions with options and recommended answers. End with: “Answer here or from the factory panel. Start your reply with `<item id>`.” Without the app use the available user-question tool.

A failure item from implement, review, QA or pr means the engine's automatic retry is spent, or the failure could not be retried blindly (a setup failure, `interactive_challenge`, `uncertain_outcome`). A refused cap remains open and waiting. Only an explicit positive increment raises the named loop's limit. `<cap id> continue: raise <limit_key> by N for this factory` approves that cap with increment N, and any text after it is an instruction for the next batch. When you ask about a cap in conversation, offer the panel's choices: +1 round (recommended), +2 rounds, or leave it waiting. A developer stop for comments records remaining items and disables further watching. Handoff needs refreshed evidence and explicit developer confirmation, never a stage-agent result.
